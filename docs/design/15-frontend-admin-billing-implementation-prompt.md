# Claude Code — Standalone Frontend, Admin Panel & Billing Implementation Prompt for AgentDisk

*This prompt builds the three pieces of scope added after the initial backend build started: the customer-facing dashboard (`apps/web`, per `03-ux-architecture-and-screens.md`/`04-claude-design-prompt.md`, already fully specified and unchanged), the new internal Staff panel (`apps/admin`, per `14-admin-panel-and-billing-design.md` PART 27–28, which is new both in schema and in screens), and Stripe billing at the confirmed "portal" depth (`14` PART 29). It assumes `11-backend-implementation-prompt.md`'s backend is real, deployed, and reachable — this prompt does not redo the core backend loop, and it does not touch Terraform/CI-CD (`12`/`13`'s scope). Copy-paste this into Claude Code as-is. It assumes `03`, `04`, `05`, `06`, `07`, `14` are available in the repo (e.g. `docs/design/`) for reference.*

## Prompt

You are building the **customer dashboard, the internal staff/admin panel, and Stripe billing** for **AgentDisk**. The backend (`apps/api`) already exists and is expected to be live and correct — this prompt's job is the two frontends that talk to it, the small amount of new backend surface `apps/admin` needs (staff auth, `/v1/staff/*`), and the billing wiring. Build exactly what the design documents specify; do not redesign the product or the screens.

### Hard Gate — Do Not Start Until This Is Verified True

Before writing any frontend code that makes a real cross-origin authenticated request, verify these against the actual live/preview deployment, not against what the docs say *should* be true:

1. **CORS is actually fixed.** `OPTIONS` preflight requests are handled *before* the auth middleware chain, the allowed origin is read from an environment-scoped binding (`env.DASHBOARD_ORIGIN`) rather than hardcoded, and it resolves to the real domains (`app.agentdisk.io` / `app-dev.agentdisk.io`) — not a placeholder. Confirm with a real `OPTIONS` request against the live dev API and check for `Access-Control-Allow-Origin`/`Access-Control-Allow-Credentials` in the response. **This was a known, previously-reported production bug (all onboarding blocked); do not assume it's fixed because a doc says it should be — check the live response.**
2. **The API-key scope naming conflict is resolved.** The API key creation/edit UI in `apps/web` (`03` §8.16/§8.17) must request and display scopes using the API's real, currently-shipped naming — bare op names (`read`/`write`/`delete`/`list`, per `05` PART 11.1/`06` PART 15.2), not a `files:read`-style UI convention that doesn't match what the backend actually stores/checks. If you find the backend and any existing UI component (e.g. a `McpToolList`-style component) still disagree, resolve toward the API's shipped naming (it's the harder side to change post-launch — real keys already exist under it) and fix the UI/display-only side to match, not the reverse.

If either of these is not actually true when you check, **stop and fix it first** (it's a backend fix, small, and already specified in `06` PART 16.8 for #1) rather than building a frontend against a backend that can't be reliably called from a browser yet. Everything below assumes both are true.

Two more backend items are *not* hard gates for this prompt but affect what you can honestly demo: audit-event logging (`05`/`06`'s `audit_events` table) must actually be called from somewhere for the Admin Panel's Audit Log screen (28.2 §7) and the customer Activity screen (`03` §8.20) to show real data — if it's still dead code when you get to those screens, wire the minimal call (append on every mutating request, from the auth middleware chain, not scattered per-handler) as part of this prompt rather than shipping a screen that's permanently empty. The hourly reconciliation cron job (`05` PART 10.8) and the Terraform workspace→directory migration are unrelated to this prompt's scope — leave them to whoever owns `11`/`13`.

### Build Order

**Phase 0 — Preflight & scaffolding.** Run the Hard Gate checks above and fix what needs fixing. Scaffold `apps/web` and `apps/admin` per `07` PART 18.6's updated structure (both are Cloudflare Pages deployables under the `apps/` monorepo root). Set up each app's build tooling, routing, and API client (`apps/admin`'s client is scoped to `/v1/staff/*` only and must never import or share auth state with `apps/web`'s client — separate cookie, separate origin, separate everything, per `14` PART 27.1/28.1). **DoD:** both apps build and serve a placeholder page locally; the Hard Gate items are verifiably true against the live/preview API, not assumed.

**Phase 1 — `apps/web`: the customer dashboard.** Build every screen in `03` PART 8 (all ~27 screens: auth, onboarding, Overview, Files/Folders browser, Agents, API Keys, Workspace settings, Members, Webhooks, Usage, Activity, Billing, Danger Zone, Active Sessions, and the rest) using the design system from `03` PART 7 (or the Claude Design export, per Read First #2) and wiring each to its real REST endpoint from `05` PART 13 — no mocked data once an endpoint exists. Active Sessions (`03` §8.23) reads from the real `refresh_tokens` table (`05` PART 11.1a) — if the backend endpoint for it doesn't exist yet, that's a backend gap to flag, not something to fake in the UI. The Billing screen (`03` §8.25) is built in this phase but its "Manage billing" button is wired in Phase 3, not here — leave it pointed at a clearly-marked stub until then. **DoD:** a real user can sign up, onboard, create an agent, mint a scoped API key (using the resolved scope naming from the Hard Gate), upload/browse/manage files, invite a member, register a webhook, and view usage/activity — all against the real live API, with no screen silently backed by fixture data.

**Phase 2a — Staff backend (`/v1/staff/*`).** Implement `14` PART 27 exactly: the `staff_users`/`staff_sessions` migrations, the fourth `audit_events.actor_type` value (`'staff'`), the `StaffScopedAccess` class (constructed only inside `/v1/staff/*` route handlers — add a lint rule enforcing this, the same discipline `06` PART 16.10 uses for parameterized queries), mandatory TOTP with no exceptions, the distinct `staff_session` cookie scoped to `admin.agentdisk.io` only, and all 12 endpoints in `14` PART 27.5's table with the three-role (`support`/`admin`/`super_admin`) matrix enforced per-endpoint. Every `StaffScopedAccess` method call appends an audit event unconditionally — no read-only exception. **DoD:** a test proves a `support`-role staff session gets `403` on every `admin`+/`super_admin`-only endpoint; a test proves every successful `StaffScopedAccess` call produces exactly one `audit_events` row with `actor_type='staff'` and the correct `staffRole`; TOTP is actually required (a password-only login attempt fails) and no staff endpoint accepts a customer bearer API key.

**Phase 2b — `apps/admin`: the staff panel.** Build the 8 screens in `14` PART 28.2 (Staff Login, Overview, Workspaces, Workspace Detail, Users, Billing, Audit Log, Staff Accounts) at the plainer visual register PART 28.1 specifies — reuse `apps/web`'s design-system tokens/components (import from the shared `packages/` layer, `07` PART 18.6), don't fork a second design system, but skip decorative elements. No customer-impersonation feature (`14` PART 28.3's explicit non-goal) — every action is *on* a workspace, never *as* the customer. **DoD:** a `super_admin` staff account can log in with TOTP, search and view any workspace and its real usage/audit data (the Audit Log screen must show real rows — confirm audit-event wiring from the Hard Gate note actually reached this screen), suspend/reinstate a workspace, and create a new staff account with a one-time TOTP QR reveal; a `support`-role account correctly cannot see the suspend/plan-override controls (hidden in the UI, and independently rejected server-side per Phase 2a).

**Phase 3 — Stripe billing.** Implement `14` PART 29 exactly: the `organizations.billing_status` migration, Stripe customer creation at org-creation time (idempotent via the existing `Idempotency-Key` pattern, `05` PART 13), `POST /v1/billing/portal-session`, and `POST /v1/webhooks/stripe` (using Stripe's SDK for signature verification, not a hand-rolled HMAC check) handling `customer.subscription.updated`/`.deleted` and `invoice.payment_failed`/`.succeeded`. Wire `billing_status` into the existing quota-check middleware step (`06` PART 15.2 step 5) so `past_due`/`canceled` blocks writes while reads keep working. Wire `apps/web`'s Billing screen "Manage billing" button (left stubbed in Phase 1) to the new portal-session endpoint. Add `STRIPE_WEBHOOK_SECRET` alongside the already-listed `STRIPE_SECRET_KEY` (`07` PART 18.2), same `wrangler secret put` discipline, dev environment uses Stripe test-mode keys only. **DoD:** a real (test-mode) Stripe subscription lifecycle — created, a simulated failed payment, a simulated recovery, a cancellation — correctly moves `organizations.billing_status` through `active → past_due → active` and `→ canceled`, and a `past_due` org is verifiably blocked from new writes (existing files stay readable) via an integration test hitting the real webhook handler with Stripe's official test event payloads, not hand-typed fixtures.

**Phase 4 — Sync & cross-check pass.** Before calling this done, re-verify the two items from the Hard Gate are *still* true against what you actually built (not just at the start): the scope-naming shown in `apps/web`'s API key UI matches what `apps/api` actually stores and checks, with zero remaining `files:read`-style strings anywhere in `apps/web`'s source; and a fresh signup on `app.agentdisk.io` (or its dev equivalent) can complete onboarding with no CORS error in the browser console. Grep both `apps/web` and `apps/admin` for any lingering placeholder domain (`agentdrive.dev`) and fix it — the design docs themselves were cleaned up in this same pass, so a leftover reference in code would now be a code-vs-docs drift in the wrong direction. **DoD:** zero drift between what the UI displays/requests and what the API accepts, verified by grep and by an end-to-end test, not by re-reading the docs and assuming they match reality.

**Phase 5 — Security & test pass.** Run `09-test-strategy-and-failure-modes.md`'s existing security suite against the now-complete system, plus these new cases this scope introduces: staff login is rate-limited at least as strictly as customer login (`06` PART 16.2's brute-force protection, applied to `/v1/staff/login`); a staff session cookie presented at `api.agentdisk.io`'s customer-facing routes is rejected (cookie scope + explicit route-level check, defense in depth); the Stripe webhook endpoint rejects a request with an invalid/missing signature; `StaffScopedAccess` cannot be instantiated from any file outside `/v1/staff/*` (the Phase 2a lint rule actually fires in CI, verified by a deliberately-broken test PR). **DoD:** all of the above pass in CI, alongside the existing full security suite — no new case is left as a manual-only check.

**Phase 6 — Deployment.** Deploy `apps/web` and `apps/admin` as separate Cloudflare Pages projects to `app.agentdisk.io`/`app-dev.agentdisk.io` and `admin.agentdisk.io`/`admin-dev.agentdisk.io` respectively (`12`'s naming standard — flat `-dev` suffix, not nested), through the same `dev`-push/`main`-PR pipeline `13` set up for the API. Confirm DNS/TLS for the two new admin subdomains (one-time, may need the human if `13`'s Terraform module doesn't already provision `cloudflare_dns_record`s for them — check before assuming). Run a real smoke test against both live URLs. **DoD:** a stranger can reach `app.agentdisk.io` and complete real signup-through-file-upload; a `super_admin` can reach `admin.agentdisk.io`, log in with TOTP, and see real fleet data — both over the actual production domain, both passing CI's smoke-test step.

### Explicitly Out of Scope for This Prompt

- Any Terraform/CI-CD change (`12`/`13`'s territory) beyond what Phase 6 needs to confirm already exists for the two new subdomains.
- A custom Stripe checkout or billing-management UI — the confirmed scope is the hosted Customer Portal only (`14` PART 29.1); do not build more than that even if it would be "nicer."
- Customer impersonation from the Admin Panel (`14` PART 28.3) — explicitly deferred, needs its own decision and its own audit design later.
- Re-litigating or re-implementing the core backend loop (`11`'s scope) — if you find a real bug there while integrating, fix the specific bug and note it, but don't restructure phases that are already built and live.

### Quality Bar

When this prompt is complete: a real customer can be onboarded end-to-end through `app.agentdisk.io` with no CORS errors and no scope-naming mismatches anywhere in the flow; a real AgentDisk staff member can be onboarded (by a `super_admin`) and use `admin.agentdisk.io` to find, inspect, and act on any customer workspace, with every action they take showing up, correctly attributed, in the Audit Log screen; and a test-mode Stripe subscription can be created, fail, recover, and cancel, with `organizations.billing_status` and write-access enforcement tracking it correctly at every step — all proven by real end-to-end tests against real (dev/preview) deployed infrastructure, not by demoing the happy path once and calling it done.
