# Claude Code — Standalone Backend-Only Implementation Prompt for AgentDisk

*This is a narrower variant of `08-claude-code-prompt.md`, scoped to the backend only: the Cloudflare Workers API, the data/storage layer, and the MCP server. It deliberately excludes the dashboard frontend (`apps/web`) — that's a separate follow-up prompt once the backend is real and testable. Copy-paste this into Claude Code as-is. It assumes `01-research-and-opportunity.md`, `05-technical-architecture.md`, `06-security-privacy-legal.md`, `07-cloudflare-deployment-and-cost.md`, and `09-test-strategy-and-failure-modes.md` are available in the repo (e.g. `docs/design/`) for reference.*

---

## Prompt

You are implementing the **backend** for **AgentDisk**, a serverless, agent-native file storage platform: a Cloudflare Workers API (REST + MCP) backed by D1 (metadata) and R2 (object storage). The full product and technical design is already finished and provided in the accompanying design documents — your job is to build exactly what's specified, not to redesign it.

**Scope of this prompt: backend only.** Build `apps/api` — the Worker, its D1 schema/migrations, its R2 integration, its REST endpoints, and its MCP server. **Do not build a dashboard, any frontend UI, or `apps/web`.** The backend must be fully usable and testable on its own via `curl`/an HTTP client and a real MCP client (e.g. the MCP inspector, or Claude Code/Claude Desktop's own MCP client) before any frontend exists — that's the point of building it standalone first.

### Before Writing Any Code

1. **Inspect the repository.** If it already contains code, read it fully before changing anything. If empty, start greenfield per the design docs.
2. **Read, in order:** `05-technical-architecture.md` (the whole thing — architecture, D1 schema, R2 design, REST API, MCP API), `06-security-privacy-legal.md` PART 15–16 (auth, authorization, the full security control list), `07-cloudflare-deployment-and-cost.md` PART 18 (environments, Wrangler config, directory structure), `09-test-strategy-and-failure-modes.md` (what "done" and "tested" mean for each piece). Skim `01-research-and-opportunity.md` for why the design decisions are what they are, if anything seems arbitrary.
3. **Produce a short `docs/IMPLEMENTATION_PLAN.md`** restating the phases below with your own task breakdown, before writing application code. Keep it short; update it as phases complete.

### Build Order

**Phase 0 — Foundation.** Scaffold `apps/api` per `07` PART 18.6's structure (`src/routes/`, `src/mcp/`, `src/services/`, `src/middleware/`, `src/db/`, `src/jobs/`, `migrations/`). TypeScript strict mode, ESLint, Prettier. Empty D1 migration. `wrangler.toml` for local dev and preview (not production yet). CI skeleton: install → lint → typecheck → test → build (full pipeline detail in `10-cicd-docs-roadmap-and-recommendation.md` PART 24 if that file is available; otherwise a standard GitHub Actions Node pipeline is fine). **DoD:** a "hello world" Worker responds on `GET /v1/healthz`, deployed to preview via CI, and `npm run build && npm test` are green.

**Phase 1 — Data layer.** Implement the full D1 schema (`05` PART 11.1/11.1a: `organizations`, `users`, `memberships`, `refresh_tokens`, `workspaces`, `agents`, `api_keys`, `folders`, `files`, `file_tags`, `audit_events`, `webhooks`) as sequential migrations. `refresh_tokens` is what backs the Active Sessions screen (`03` §8.23) and refresh-token-rotation/reuse detection (`06` PART 15.1/16.6) — don't skip it just because it's easy to overlook next to the more obviously load-bearing tables. Magic-link and password-reset tokens are *not* a D1 table — implement them as short-TTL KV entries per `05` PART 11.1a. Implement the `WorkspaceScopedFiles`-style repository pattern (`06` PART 16.1) for every table that pattern applies to — this is the tenant-isolation mechanism and must exist before any route handler touches the database. **DoD:** migrations apply cleanly to a fresh D1 instance; unit tests prove a repository scoped to workspace A returns zero rows for workspace B's data even when asked directly (not just that a higher layer would have blocked the request).

**Phase 2 — Authentication & authorization.** Implement human auth: email/password (Argon2id hashing, `06` PART 16.5) and magic link, session + refresh-token cookies with rotation (`06` PART 15.1/16.6). Implement API-key auth: generation (`crypto.getRandomValues`, `ask_live_`/`ask_test_` prefixes), hashing (SHA-256, never store plaintext), scope model (`{ops, pathPrefix}`), expiry, and revocation with immediate KV-cache invalidation (`06` PART 15.3). Implement the full authorization middleware chain (authenticate → resolve scope → resolve workspace → authorize → check quota → invoke handler, `06` PART 15.2/16.1) as the single place every request passes through. Do not implement GitHub OAuth in this pass — stub the interface so it can be added later without restructuring auth, but don't build it now (OAuth is a dashboard-adjacent, later concern). **DoD:** signup → verify email → login → authenticated request → logout work end-to-end against a real local/preview D1, with real tests (not mocks); an expired, revoked, or forged token is rejected with the exact error codes and shapes from `06` PART 17.4 / `05` PART 13.

**Phase 3 — Storage core (R2 + files/folders).** Implement the R2 object-key strategy (`tenant/{workspaceId}/{fileId}`, `05` PART 12.1), presigned upload/download (`05` PART 12.2/12.3), multipart upload for large files with resumability (`05` PART 12.7), folder CRUD, file CRUD (create/get/list/update/move/copy/delete/restore), quota enforcement at write time using the plan limits table (`07` PART 19.0), soft-delete plus the hourly reconciliation Cron job (`05` PART 10.7/10.8). Implement path validation/normalization (`06` PART 16.12) as one shared, heavily tested utility — write explicit tests with real `../../`-style payloads proving rejection, not assumed safety. **DoD:** a real file uploads via a presigned URL, lists, downloads, moves, gets deleted, and gets restored within the grace period — all proven by integration tests against a real preview R2 bucket and D1 instance, not mocks.

**Phase 4 — REST API.** Implement every endpoint in `05` PART 13's table with the uniform error envelope and full error-code catalogue (`06` PART 17.4). Generate `openapi.yaml` from the route definitions (or write it by hand as the source of truth and generate route types from it — pick one direction and don't let them drift, per `01` PART 2.10's documented AgentStorage failure to avoid repeating). Implement rate limiting per `05` PART 10.9: Cloudflare WAF rules for coarse/no-auth-endpoint protection, KV counters for per-key/per-session limits. **DoD:** every endpoint has a happy-path test and an authorization-denial test; the generated OpenAPI spec passes a contract check against the actually-deployed API in CI.

**Phase 5 — MCP server.** Implement the MCP endpoint (`POST /mcp`, Streamable HTTP transport, JSON-RPC 2.0, `05` PART 14.2) as a thin layer calling the *same* service functions Phase 4's REST handlers call — if any business logic gets duplicated between a REST handler and an MCP tool handler, stop and refactor to share it. Implement all 10 MVP-1 tools from `05` PART 14.4 (`list_files`, `search_files`, `get_file`, `create_file`, `update_file`, `delete_file`, `create_folder`, `move_file`, `copy_file`, `get_metadata`) plus `search_content`'s honest `indexingNotEnabled` stub. Filter `tools/list` to only what the presented key's scope permits. Implement per-session strict rate limiting via the Durable Object pattern (`05` PART 10.9/14.3) specifically to bound a looping/misbehaving agent. **Library note (verified against Cloudflare's own docs, Sept 2026):** Cloudflare's Agents SDK now recommends `createMcpHandler()` for new, stateless remote MCP servers and marks the older `McpAgent` (Durable-Object-backed) class as deprecated for this use case — this matches, not conflicts with, the `05` PART 14.1 decision to run MCP inside the same stateless Worker fleet as REST. Build the MCP endpoint as a stateless handler; the *only* Durable Object in this system is the narrow per-session rate-limit counter above, not a stateful `McpAgent` wrapping the whole tool surface — don't reach for `McpAgent` for that. Also note Cloudflare's canonical remote-MCP quickstart auth pattern is OAuth (GitHub/Google/etc., via an `OAUTH_KV` namespace) for the "human authorizes a third-party client" use case — that's a different scenario from AgentDisk's agent-native bearer-API-key model (`05` PART 14.2/15.3), which is MCP-spec-valid and intentional; don't substitute OAuth for it without an explicit decision to do so. **DoD:** a real MCP client (test against the MCP inspector tool, or Claude Code/Claude Desktop's own MCP client pointed at your local/preview deployment) connects, discovers only its scope's tools, and successfully calls each one; a scope-violating call returns a correct MCP-shaped error, not a silent no-op or a raw 500.

**Phase 6 — Security hardening pass.** Walk `06-security-privacy-legal.md` PART 16 top to bottom against the actual implementation, not the design intent: CSRF (relevant for any cookie-authenticated admin/internal routes this backend exposes), CORS policy, parameterized-query enforcement (add a lint rule banning string-built SQL if one doesn't exist), SSRF protection on webhook URLs (`06` PART 16.11 — validate at both registration and delivery time), secret redaction in logs (`06` PART 16.17/16.18), webhook-secret encryption at rest (`06` PART 16.16a). Run the full security test-case table from `09-test-strategy-and-failure-modes.md` PART 22.1 (SEC-01 through SEC-21) against the real deployed backend. **DoD:** all 21 security test cases pass; any dependency/static-analysis findings are fixed or explicitly documented as accepted, never silently ignored.

**Phase 7 — Testing completion & deployment.** Fill any remaining gaps against `09`'s unit/integration/performance matrix (PART 21, PART 22.2 — specifically seed 10,000 files in a test workspace and verify list/search stay fast via cursor pagination, not `OFFSET`). Deploy to production per `07-cloudflare-deployment-and-cost.md` PART 18.3 (create production D1/R2/KV/Queues resources, configure secrets via `wrangler secret put`, run migrations, deploy the Worker, configure `api.` and `mcp.` subdomains). Run the smoke-test suite against the live production URL. **DoD:** the backend is live, every test tier is green, and a real `curl` against production plus a real MCP client connection both work end-to-end.

### Explicitly Out of Scope for This Prompt

- The dashboard frontend (`apps/web`) — every screen in `03-ux-architecture-and-screens.md` and the design produced from `04-claude-design-prompt.md`. Build that against this backend's finished, stable API in a separate pass.
- GitHub OAuth, Stripe billing, the audit-log UI, team-member management UI — these are dashboard-dependent or explicitly MVP-1-sequenced-after-core-loop per `02-product-and-mvp-scope.md` PART 6. The backend's data model and API should already support what they need (the schema and endpoints don't change), but don't build the OAuth callback flow or Stripe webhook handling in this pass unless asked.
- The generated docs site (`apps/docs`) — a later, low-effort step once `openapi.yaml` is stable.

### Coding Principles (non-negotiable, same bar as the full build)

TypeScript strict mode everywhere, no unexplained `any`. Modular architecture — route/tool handlers are thin, business logic lives in `services/`. Minimize dependencies; use Workers' built-ins (Web Crypto, `fetch`) before reaching for an npm package, and nothing that assumes a long-running Node process. No unnecessary infrastructure — no Redis, no managed Postgres, no container platform; if you believe one is genuinely required, stop and present it as a decision (format below) rather than adding it silently. Secure defaults on every new endpoint. Environment variables and `wrangler secret` for all config/secrets — never hardcoded, never committed; update `.dev.vars.example` and `07`'s secrets list when you add one. Input validation at every boundary using one consistent validation library, chosen in Phase 0. Structured errors (`06` PART 17.4) and structured, redacted logging (`06` PART 16.18) everywhere. Deterministic tests — no wall-clock races, no unseeded randomness, no silent external network dependency. Avoid premature abstraction — build the concrete thing the design specifies, generalize only when a second real case appears.

### Testing/Lint/Typecheck/Build Discipline

After every phase (and any significant sub-feature within one): run the full test suite, linter, type checker, and build. Fix failures before moving on — never advance with a red suite, a lint error, a type error, or a broken build. Never silently skip, mock-away, or comment out a failing test; fix the test if it's wrong, fix the code if it's wrong, and say which. Never mock R2 or D1 in a test tier that's supposed to prove real integration — reserve mocks for true unit tests of isolated logic. Never leave a `TODO` for core functionality the design documents describe — implement it, or flag it as a deferred decision using the format below.

### When to Stop and Ask

Continue autonomously through everything the design documents cover. Stop only for a genuine, undocumented, hard-to-reverse decision (e.g., which validation library, which specific email/AI-provider name to wire in if that becomes relevant to the backend, or a real architectural fork the docs left open). Use exactly this format:

```
Decision required:
Option A: <description>
Option B: <description>
Recommendation: <which, and why>
Reason: <the tradeoff driving the recommendation>
Impact: <what happens if we proceed with the recommendation vs. wait for an answer>
```

Do not stop for anything a competent senior engineer would just decide from the docs or convention — make the call, note the assumption in a comment or the implementation plan, and keep going.

### Quality Bar

When this prompt is complete, a stranger with `curl` and an MCP client — no dashboard, no UI — should be able to: create a workspace, get a scoped API key, create an agent, upload a file (small inline and large multipart), list/search/move/copy/delete it, connect an MCP client and do the same through tools, and trigger every documented error case and get back the exact, correct, human-and-agent-legible error from the catalogue. Tenant isolation must be provably unbreakable under the test suite, not just "should be fine by construction." That's the bar — not "the happy path works when I demo it myself."
