### PART 21–23 of the AgentStorage-Inspired Platform Design

All content is **PROPOSAL**.

## PART 21 — Test Strategy

### 21.1 Unit Tests (fast, no network, no real D1/R2 — pure logic)

| Area | What's covered |
|---|---|
| Authentication | Password hashing/verification round-trip, magic-link token generation/expiry, session JWT sign/verify, refresh-token rotation logic, generic-error-on-failure behavior (never distinguishing "no such user" from "wrong password" in the returned error) |
| Authorization | Role-check logic (owner/admin/member matrix against every route's required role), API-key scope-intersection logic (sub-key can never exceed parent scope), path-prefix-match logic |
| API keys | Key generation entropy/format, hash generation, prefix/last-four derivation, expiry check, revocation check, KV-cache invalidation call on revoke |
| Path validation | Rejects `..` segments, rejects non-`/`-leading paths, rejects over-length/over-depth paths, normalizes Unicode consistently, accepts all valid path shapes used elsewhere in the test suite |
| Quota calculations | Storage-byte accumulation math, file-count math, egress-counter math, plan-limit lookup, boundary conditions (exactly-at-limit, one-byte-over) |
| File metadata | MIME/size/checksum field validation, tag normalization (dedup, case handling), custom-metadata JSON size cap enforcement |
| Permission checks | The `WorkspaceScopedFiles`-style repository pattern (`06` PART 16.1) — specifically, that it is *structurally* impossible to construct a query without a `workspace_id` bound from server-side context, tested by attempting to call the repository with no workspace context and asserting it's a compile-time or immediate-runtime error, not a silent no-filter query |

### 21.2 Integration Tests (against real Miniflare/preview D1 + R2, no mocks for the thing being tested)

| Area | What's covered |
|---|---|
| Worker + D1 | Migrations apply cleanly; repository layer performs correct CRUD against a real D1 instance; cross-tenant query attempts return zero rows (not an error — proving the `WHERE workspace_id = ?` clause actually executes, not just that authorization blocked the request earlier) |
| Worker + R2 | Presigned URL generation and actual upload/download against a real R2 bucket (preview environment); multipart upload completes correctly for a file above the threshold; object key strategy (`tenant/{workspaceId}/{fileId}`) is verified by direct R2 inspection after a create |
| API + database | Full request→D1 round trip for every REST endpoint, including quota-rejection paths |
| API + storage | Full request→R2 round trip for upload/download/delete, including the soft-delete-then-reconciliation-purge sequence (run the reconciliation job manually in-test rather than waiting for the real Cron schedule) |
| MCP + authorization | An MCP client session with a narrowly-scoped key sees only the tools its scope allows via `tools/list`, and a `tools/call` for a disallowed tool is rejected with the correct MCP error shape, not silently executed |

### 21.3 End-to-End Tests (Playwright, against a deployed preview environment, real browser)

Signup → email verification → login → create workspace (if not auto-created at signup) → create agent → create API key (reveal-once modal behaves correctly, key is copyable, modal cannot be dismissed without acknowledgment) → upload a file via the dashboard → browse to it → rename it → move it → download it → delete it (confirm modal) → create a folder → connect MCP (copy config, verify placeholder-vs-real-key checkbox behavior) → agent reads a file via a live REST call using the created key → agent writes a file via a live REST call → an intentionally out-of-scope agent request is rejected with `403` and the UI/API error matches the catalogue (`06` PART 17.4).

### 21.4 What "Deterministic" Means Here

No test relies on wall-clock races (a "wait 60 seconds for cooldown" UI test uses a mocked/injectable clock, not a real 60-second sleep); no test relies on unseeded randomness (ULID/token generation is tested against a fixed seed or by asserting format/entropy properties, not specific values); no integration/E2E test silently depends on an external network call that isn't either pointed at a real preview-environment resource or explicitly, visibly mocked.

## PART 22 — Detailed Test Cases

### 22.1 Security Test Cases

| ID | Preconditions | Steps | Expected Result | Severity |
|---|---|---|---|---|
| SEC-01 | User A and User B each own a workspace with files | User A's authenticated session requests `GET /v1/files/:id` for a file ID belonging to User B's workspace | `404 NOT_FOUND` (not `403` — do not confirm the resource exists to an unauthorized caller) | Critical |
| SEC-02 | Agent A's key is scoped to Workspace A; Workspace B exists with files | Agent A's key calls `GET /v1/files/:id` for a file in Workspace B | `404 NOT_FOUND` | Critical |
| SEC-03 | Two distinct workspaces exist | A request authenticated for Workspace A includes a `workspaceId` referencing Workspace B in any request body/query param | The server-resolved workspace (from the authenticated identity) is used; the client-supplied `workspaceId` is ignored or triggers `403` if used only for disambiguation among the caller's own workspaces and doesn't match | Critical |
| SEC-04 | An API key with `expires_at` in the past exists | The expired key is used to call any endpoint | `401 UNAUTHORIZED`, generic message; confirmed even if the key was cached in KV prior to expiry (reconciliation sweep, `05` PART 10.8, has evicted it) | High |
| SEC-05 | An API key is revoked mid-session | The revoked key is used within seconds of revocation | `401 UNAUTHORIZED` — KV cache bust on revoke (`06` PART 15.3) verified to take effect immediately, not after a TTL window | Critical |
| SEC-06 | — | A request presents a syntactically invalid bearer token (wrong prefix, wrong length, garbage string) | `401 UNAUTHORIZED`, no stack trace or internal detail leaked | High |
| SEC-07 | A workspace and folder exist | A `path` field is submitted containing `../../` segments | `400 VALIDATION_ERROR` before any D1/R2 operation; verify via test that no R2 object outside the tenant prefix was touched | Critical |
| SEC-08 | — | A filename containing HTML/script payloads (`<img src=x onerror=alert(1)>`), null bytes, or extremely long strings is submitted as a file name/caption/tag | Stored as an opaque, escaped string; rendered safely in the dashboard (no script execution); rejected outright if it exceeds length limits | High |
| SEC-09 | Workspace on Free plan (max file size configured) | An upload attempts to exceed the plan's max-file-size | `413 PAYLOAD_TOO_LARGE` at presigned-URL-generation time, and independently re-enforced at the `complete` step even if the client bypassed the declared size | High |
| SEC-10 | — | A file is uploaded with `mimeType: "image/png"` but actual bytes are an HTML/JS payload | File is stored and served with the declared/stored MIME type but the dashboard never renders arbitrary content as live HTML regardless of declared type (`06` PART 16.13) — verify no script executes when the file is previewed | High |
| SEC-11 | A file exists that the caller's key has no `read` scope over | The caller requests `GET /v1/files/:id/download` | `403 FORBIDDEN` or `404` per SEC-01's resource-hiding rule (consistent choice) — no download URL is ever generated | Critical |
| SEC-12 | A signed URL was generated with a 1-hour expiry | The URL is used after 61+ minutes | R2 rejects the expired signature; client receives an R2-native expiry error, and the dashboard's own "copy link" flow independently checks/refreshes rather than trusting a stale cached URL | Medium |
| SEC-13 | A valid signed webhook payload was captured | The identical payload (same `eventId`/signature) is replayed after 6+ minutes | Receiver-side guidance (and our own webhook-consuming code, if any) rejects based on timestamp age; `eventId` dedup independently blocks a replay even within the window | Medium |
| SEC-14 | — | 6 failed login attempts within 15 minutes from the same account | 6th+ attempt returns a lockout response with countdown, distinct from the generic wrong-credentials message, per `06` PART 16.2/PART 8.7 | High |
| SEC-15 | A per-key rate limit is configured | A client distributes requests across many source IPs/Cloudflare PoPs to attempt to exceed a KV-based counter's consistency window | Some slop may occur (documented, accepted trade-off per `05` PART 10.9/16.14) but the strict DO-backed MCP session limiter (`05` PART 14.3) is verified to hold exactly, not approximately | Medium |
| SEC-16 | Dashboard origin is `app.agentdisk.io` (read from `env.DASHBOARD_ORIGIN`, never hardcoded — `06` PART 16.8) | A request with cookie credentials arrives with `Origin: https://evil.example` | Rejected — `Access-Control-Allow-Credentials` is not set for unrecognized origins; the request is blocked by CORS at the browser layer for any legitimate browser-based attack vector, and server-side CSRF-token check independently blocks it even if CORS were somehow bypassed | Critical |
| SEC-17 | — | A filename/caption/tag field contains a crafted XSS payload and is viewed by another authorized workspace member in the dashboard | No script executes; payload renders as inert text | Critical |
| SEC-18 | — | A `path`, `caption`, `tag`, or `search query` field contains SQL-meta-characters (`' OR 1=1 --`, etc.) | No behavioral difference from any other string — parameterized queries mean the input is inert data, never interpreted as SQL; verify via a test that asserts the exact same code path (prepared statement, bound parameter) is used regardless of input content | Critical |
| SEC-19 | — | A request to any workspace-scoped endpoint omits any resolvable tenant context (no valid session, no valid API key) | `401 UNAUTHORIZED` — no endpoint (other than the explicitly public set: `/v1/workspaces` POST, `/v1/healthz`) proceeds without a resolved `workspace_id` | Critical |
| SEC-20 | Attacker controls a request but not a valid credential for the target workspace | Attacker forges/guesses a `workspaceId` value and submits it without a credential scoped to that workspace | `401`/`403` — a `workspaceId` alone, without an authenticated identity that's actually a member/scoped to it, grants nothing (see SEC-03's stricter framing: the server never trusts client-supplied tenant identifiers as an access grant) | Critical |
| SEC-21 (IDOR) | Two files exist with sequential or guessable-looking IDs (ULIDs are not sequential, but this test exists specifically to prove that property, not assume it) | An authenticated caller for Workspace A enumerates/guesses IDs attempting to access Workspace B's files by ID alone | Every ID lookup is still filtered by `workspace_id` server-side (SEC-01's mechanism) regardless of whether the ID itself is guessable — the defense is authorization-by-workspace, not security-by-unguessable-ID, though ULIDs additionally aren't practically enumerable | Critical |

### 22.2 Performance Test Matrix

| Scenario | What's measured | Target / expected bottleneck |
|---|---|---|
| 1 file in a workspace | Baseline latency for list/get/upload/download | Sub-100ms for metadata operations (D1 read, colocated with Worker); upload/download latency dominated by R2 transfer time, not Worker overhead |
| 100 files in a folder | List/search pagination correctness and latency | List latency should not meaningfully differ from the 1-file case (indexed query, paginated) — if it does, the index (`idx_files_workspace_path`) is missing or misused |
| 10,000 files in a workspace | List/search at scale, D1 query-plan behavior | Verify pagination (`cursor`) remains performant (no `OFFSET`-based pagination, which degrades at this scale — confirm cursor-based `WHERE id > ?` style pagination is actually implemented, not just documented) |
| Large files (near the plan's max-file-size cap) | Multipart upload correctness, presigned URL part count, complete-step latency | Multipart threshold (100MB default) correctly triggers part-based flow; a single-part upload near but under the threshold succeeds without unnecessary multipart overhead |
| Concurrent uploads (many files, same workspace, simultaneously) | Quota-counter correctness under race | The optimistic-reserve-then-commit pattern (`05` PART 12.2 step 2) is tested specifically for the race where two concurrent uploads could both pass a "does this fit?" check before either commits — verify the reservation step actually prevents overshoot, not just usually-prevents-it |
| Concurrent API requests (many keys, many workspaces, simultaneously) | Cross-tenant isolation holds under load, no shared-state bleed | Run the SEC-01–03 test class under concurrent load, not just sequentially, to catch any accidental shared-mutable-state bug in request handling |
| Concurrent agents (many keys within one workspace, simultaneously) | Per-workspace quota and rate-limit correctness under real multi-agent load (this is a first-class expected usage pattern per the persona design, `02` PART 5.1 Persona 3/4) | Quota counters converge correctly even under sustained concurrent write pressure from several agents in one workspace |
| Search performance | Latency of `GET /v1/search` at 10,000+ files, with and without tag filters | Confirm the `file_tags` index and `idx_files_name` are actually used by the query planner (inspect via D1's query-plan tooling if available) — this is the most likely accidental full-scan bottleneck if an index is missing |

**Identified likely bottlenecks (to watch for specifically, not just generically test):** `OFFSET`-based pagination degrading at high file counts (mitigated by cursor pagination, verify it's real); the KV-based quota fast-path counter drifting under high concurrent write rates before the D1 durable write catches up (mitigated by the reconciliation job, `05` PART 10.8 — verify drift stays bounded and self-corrects); D1's single-writer-per-database model under very high concurrent write volume at the top end of the "10,000+ users" growth stage (`07` PART 19.3) — this is the honest ceiling flagged in the D1-vs-Postgres ADR (`05` PART 10.3) and the specific signal that would trigger evaluating a Postgres migration path, not a problem expected at MVP-0/1 scale.

## PART 23 — Failure Mode Analysis, Data Consistency, Backup & Recovery

### 23.1 Failure Mode → Recovery Behavior

| Failure | Recovery behavior |
|---|---|
| **R2 temporarily unavailable** | Upload/download requests fail fast with a `503`-class error and a client-facing "Storage is temporarily unavailable, please retry" message (not a generic 500) so clients/agents can distinguish "retry shortly" from "something is wrong with your request." Metadata operations (list, search) that don't touch R2 continue to work normally, since they're D1-only. |
| **D1 unavailable** | Nearly everything degrades, since D1 is the metadata source of truth — the API returns `503` for any D1-dependent operation. KV-cached data (e.g., a recently-verified API key's scope) can still authorize a request briefly from cache, but any operation requiring a fresh D1 read/write fails closed (denies, does not silently proceed on stale/assumed data). |
| **Worker throws an unhandled exception** | Caught by a top-level error boundary in the Worker entrypoint, logged (redacted per `06` PART 16.18) with a request ID, and returned to the client as `500 INTERNAL_ERROR` with that request ID surfaced (so a support conversation can reference it) — never a raw stack trace or internal detail in the response body. |
| **Queue processing fails (a job errors)** | Cloudflare Queues' built-in retry (configured `max_retries`, `07` PART 18.2) re-attempts; after retries are exhausted, the job lands in the dead-letter queue (`agentdisk-jobs-dlq`) rather than being silently dropped, and a DLQ-depth alert (`07` PART 18.5) notifies the team. Webhook-delivery failures specifically are also surfaced to the customer (a "last delivery failed" indicator on the webhook's settings row, V2 UI) rather than failing silently from their perspective too. |
| **AI provider fails (V2 async processing)** | The processing job is marked `failed` in the file's metadata (not left `pending` forever); the file itself remains fully usable (upload was never blocked on this — `05` PART 10.6) — only the optional derived metadata/summary/embedding is missing, and a retry can be triggered manually or by the next scheduled sweep. |
| **Signed URL expires mid-use** | Client receives R2's native expiry error on the request that uses it; the dashboard's UI-driven download/share flows regenerate a fresh URL transparently on next use rather than surfacing the raw R2 error to a human. |
| **Upload interrupted (network drop mid-transfer)** | The `files` row remains `status='pending'`; no partial R2 object is considered valid (R2 multipart uploads are atomic per part, and an incomplete multipart upload is either explicitly aborted or swept by the reconciliation job's pending-upload timeout, `05` PART 10.8, which also releases the reserved quota). The client can safely retry the same logical upload (using the same `Idempotency-Key`) without double-reserving quota. |
| **User closes browser mid-upload** | Same as the network-drop case — the pending row times out and is cleaned up; nothing is left in a half-committed, quota-consuming-forever state. |
| **Agent retries indefinitely (a loop)** | The MCP per-session strict rate limiter (`05` PART 14.3, Durable-Object-backed) and the general per-key rate limits (`05` PART 10.9) bound the damage; sustained hard-limit hits are visible in the Activity log (`03` PART 8.20) and, at a severe threshold, could trigger an automatic temporary key suspension with notification (V2 — flagged as a candidate hardening feature, not committed for MVP-1). |
| **Database transaction fails (partial write)** | D1 supports single-database transactions for multi-statement operations that must be atomic (e.g., creating a file row and decrementing/incrementing related counters in one transaction) — these use D1's transaction/batch API rather than sequential unguarded statements, so a mid-sequence failure rolls back rather than leaving a half-applied state. |
| **Metadata exists but R2 object does not** | Detected by the reconciliation job (`05` PART 10.8) via periodic spot-checking (or lazily, the first time a `GET download` for that file fails against R2 despite an `active` D1 row) — the file is marked `status='failed'` with a clear error surfaced to the caller ("This file's contents are missing. Please contact support or re-upload.") rather than serving a broken download link silently. |
| **R2 object exists but metadata does not** | This should be structurally rare given the object-key strategy (objects are only ever written by the Worker as part of a metadata-creating flow), but the reconciliation job's periodic R2-listing-vs-D1 cross-check (V2 hardening — MVP-1 relies on the structural guarantee rather than active cross-checking) would flag an orphaned object for cleanup rather than leaving invisible, unaccounted-for storage silently accruing cost. |

### 23.2 Data Consistency Model

**PROPOSAL — stated honestly, not overclaimed.** R2 and D1 are **not** one ACID transaction — there is no distributed-transaction coordinator across them, and this design does not pretend otherwise. The consistency strategy is instead: (1) **order operations so the source of truth (D1) is only updated to "active" after R2 confirms the bytes exist** (upload: R2 write happens, *then* the `complete` call flips D1 to active — never the reverse, so a crash between steps leaves an inert `pending` D1 row and possibly an orphaned R2 object, never a D1 row claiming success for bytes that don't exist), (2) **make destructive operations eventually consistent in the safe direction** (delete: D1 is marked deleted first — the fast, safe half — R2 purge happens asynchronously after; a crash here leaves a D1-says-deleted, R2-still-has-the-bytes state, which is *safe* — it just means the reconciliation job has cleanup to do, never a security or correctness problem, since a deleted D1 row is already inaccessible via the API), and (3) **usage counters are eventually consistent by design** (KV fast-path counters can drift briefly from the D1-durable truth; the hourly reconciliation job recounts and corrects — quota enforcement uses the fast-path counter for the immediate check, accepting a small window of possible slight overshoot, in exchange for not making every single write synchronously wait on a strongly-consistent global counter, which would be a real latency/cost tradeoff not worth making for a soft quota boundary that's corrected within the hour regardless). Audit events are append-only and best-effort-immediate (written via `waitUntil` so they don't block the response, but virtually always land before the response reaches the client in practice) — a lost audit event on an extremely rare Worker-crash-mid-request edge case is an accepted, disclosed gap, not a claimed impossibility.

**What genuinely requires a transaction:** any multi-row D1 write that must be all-or-nothing within the metadata layer itself (e.g., moving a file — updating its `path` and adjusting any folder-level counters together) uses D1's batch/transaction API. **What is intentionally eventually consistent:** usage counters (self-correcting hourly), R2-object cleanup after a soft-delete (self-correcting via the reconciliation job), and cross-service consistency between D1 and R2 generally (protected by the ordering discipline in the previous paragraph, not by a transaction that doesn't exist).

### 23.3 Backup & Recovery

**Database backup.** D1 supports point-in-time recovery within Cloudflare's retention window; additionally, a scheduled export (via the reconciliation Cron Worker or a separate daily job) writes a full D1 snapshot to a dedicated R2 bucket (`agentdisk-db-backups`, distinct from the files bucket, with its own lifecycle rule retaining, e.g., 30 daily snapshots) — belt-and-suspenders beyond Cloudflare's own platform-level recovery, and something the team directly controls and can test restores from.

**Migration recovery.** Migrations are forward-only and version-controlled (`07` PART 18.2); if a migration is discovered to be wrong after deploy, the fix is a new forward migration correcting the issue, never an edit to an already-applied migration file — this keeps every environment's migration history reproducible and prevents the classic "works on my machine because my local migration history diverged" class of bug.

**Accidental deletion.** File-level: the 24-hour soft-delete grace period (`05` PART 12.5/12.6) plus `POST /v1/files/:id/restore`. Workspace-level: workspace deletion (`03` PART 8.21) is a deliberately high-friction action (type-to-confirm) but is **not** currently designed with its own grace period in MVP-0/1 — this is an explicit, disclosed gap: **PROPOSAL for V2 hardening** — extend the same soft-delete-plus-grace-period pattern to workspace deletion, not just file deletion, given how much more is at stake in that single action; flagged here rather than silently assumed safe.

**R2 recovery.** Within the soft-delete grace period, trivial (the object was never actually purged). Beyond it, recovery depends on the daily D1-snapshot/R2-backup-bucket strategy above only insofar as it can restore *metadata* — actual file *bytes* purged from R2 after the grace period are **not** separately backed up in MVP-0/1 (this would roughly double storage cost for a low-probability scenario, a deliberate cost/risk tradeoff, disclosed here rather than silently assumed). If a customer needs stronger guarantees, R2 bucket versioning (`05` PART 12.7, V2) is the correct upgrade path, offered as a plan feature rather than a default cost for every workspace.

**Account deletion.** Follows the Privacy Policy's stated process (`06` PART 17.2 Section 14) — blocked if the user is the sole owner of other workspaces, otherwise proceeds through the same soft-delete-then-purge pattern as workspace deletion.

**Disaster recovery.** Cloudflare's platform (Workers, R2, D1) is itself multi-region/globally-distributed by default — this product does not implement its own multi-region failover, because doing so would mean re-implementing what the underlying platform already provides, which is realistically **the correct, honest answer given the chosen architecture**: our disaster-recovery posture is "as good as Cloudflare's own platform reliability, plus our own D1-snapshot-to-R2-backup-bucket layer for logical (not physical) recovery from an application-level data-corruption bug (e.g., a bad migration or a bug that mass-deletes rows) that Cloudflare's own infrastructure redundancy wouldn't protect against." This is stated plainly rather than claiming a formal RTO/RPO commitment the team hasn't actually built or tested — a real RTO/RPO target and a tested restore drill are a V2/production-hardening milestone (`10-cicd-docs-roadmap-and-recommendation.md` PART 26), not a day-one claim.
