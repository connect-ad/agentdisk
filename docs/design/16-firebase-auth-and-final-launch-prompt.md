## PART 30 — Firebase Authentication (Replaces PART 15.1/16.5/16.6/16.7's Original Design)

### 30.1 Why Firebase, and Exactly What It Owns vs. What Stays on Cloudflare

Your own read of the split was correct in substance, with one nuance worth being precise about: it's not that Firebase "hands off" a session to Cloudflare which Cloudflare then owns independently — Firebase stays in the loop for the life of every session, as the thing that issues and re-issues the credential. Concretely:

**Firebase owns:** email/password signup and login, Google sign-in, GitHub sign-in, email-link (passwordless "magic link") sign-in, password reset, email verification, and the session/token machinery underneath all of that — a short-lived (1-hour) ID token plus a long-lived refresh token that the Firebase client SDK holds and silently renews, entirely inside the browser. AgentDisk's backend never receives, stores, or even sees a password.

**Cloudflare (unchanged) owns:** everything after "who is this person" — organizations, workspaces, storage, agents, API keys, permissions/scopes, quotas, billing, audit logs. Every one of those is exactly as designed in `05`/`06` PART 15.2 onward; none of it moves.

**The join:** once signed in, the Firebase SDK attaches the current ID token as a bearer `Authorization` header on every request to `api.agentdisk.io`. The Worker verifies that token itself (30.2) and, on a valid token, resolves it to an AgentDisk `users.id` via `firebase_uid` (`05` PART 11.1) — from that point on, every existing authorization/tenant-isolation mechanism (`06` PART 16.1) runs exactly as before, unaware that the identity behind it came from Firebase rather than a first-party session.

**Cost check (verified against Firebase's own pricing page, Sept 2026):** email/password and federated OAuth sign-in (Google, GitHub, and others) are free on both Firebase's Spark and Blaze plans, with no per-monthly-active-user charge at any volume. The only Authentication features that cost anything are phone/SMS verification (billed per SMS) and enterprise SAML/OIDC beyond a small free quota — neither used here. This is a materially better answer than the per-MAU vendor cost this project's cost model (`07` PART 19.2) originally worried about when it ruled out a "per-MAU auth vendor" — that reasoning was sound against Auth0-shaped pricing, it just doesn't describe how Firebase's standard auth methods are actually priced.

### 30.2 How the Worker Verifies a Firebase ID Token — No Admin SDK, No Node Dependency

This is the part worth being precise about, because it's the one place a wrong assumption would break everything: **the Firebase Admin SDK does not run in Cloudflare Workers** (it's a Node-targeted SDK). That's fine — verifying a Firebase ID token is "just" JWT verification, and that's fully doable with the Web Crypto API Workers already provide, which is why this is a well-established community pattern (independently documented by multiple write-ups, and packaged as a small library, `firebase-auth-cloudflare-workers`, that does exactly this).

The Worker's verification, on every authenticated request:
1. Extract the bearer token from `Authorization: Bearer <idToken>`.
2. Look up the signing key by the token's `kid` (key ID) header against Google's public JWKS, fetched from `https://www.googleapis.com/service_accounts/v1/jwk/securetoken@system.gserviceaccount.com` and **cached in Workers KV** (the same KV namespace pattern already used elsewhere in this design, `05` PART 10.1) — respecting the `Cache-Control` max-age Google's response sends, refetching only on a cache miss or an unrecognized `kid` (which happens on Google's own key rotation, roughly every few weeks).
3. Verify the RS256 signature via `crypto.subtle.verify`.
4. Check claims: `iss` must equal `https://securetoken.google.com/<FIREBASE_PROJECT_ID>`; `aud` must equal `FIREBASE_PROJECT_ID`; `exp` must be in the future; `iat` must be at or after the caller's `users.session_revoked_after` (30.4).
5. On success, `sub` is the Firebase UID — resolve or provision the matching `users` row (30.3) and proceed into the existing authorization middleware chain exactly as before.

No secret is required to *verify* a token (JWKS are public keys); `FIREBASE_PROJECT_ID` itself isn't sensitive either, but it's still set as an environment-scoped value per `07` PART 18.2 (already updated) so dev and prod point at two different Firebase projects (30.5) without any hardcoding.

### 30.3 What Changed in the Data Model (Already Applied to `05`)

- `users.firebase_uid` (unique, indexed) replaces `password_hash` and `oauth_github_id` — the only thing distinguishing one human account from another on AgentDisk's side is now this join key.
- The `refresh_tokens` table is gone entirely — Firebase's client SDK owns refresh-token issuance, storage, and rotation, and AgentDisk's backend never sees one.
- `users.session_revoked_after` (unix ms, default 0) is new — see 30.4.

### 30.4 "Log Out Everywhere" Without a Refresh-Token Table

Firebase's own answer to this — `revokeRefreshTokens()` plus `verifyIdToken(token, checkRevoked: true)` — is **Admin-SDK-only** (Node/Java/Python/Go/C#), and Firebase's own documentation is explicit that checking revocation status this way costs "an extra network round trip" on every single verification, which is not something to do on every request from a stateless Worker fleet.

AgentDisk's replacement, which is both cheaper and more first-party: **`users.session_revoked_after`.** Set it to `now()` whenever a user chooses "Log out everywhere" (or a staff member forces it on their behalf, `14` PART 27.5's `force-logout` endpoint). Every request's auth middleware already loads the `users` row to resolve identity — comparing the token's `iat` against this column costs nothing extra, no added round trip, no second table. A token issued before the cutoff is rejected with a normal 401 even though it's still cryptographically valid and unexpired; the Firebase SDK then silently mints a fresh ID token from the refresh token it already holds and retries, which carries a fresh `iat` and passes.

**Stated plainly, this is a real, bounded limitation, not a complete substitute for Firebase's own revocation:** it doesn't invalidate the underlying Firebase refresh token, so it achieves "every other active session is forced to quietly re-prove itself" (instant, and sufficient for the common "I left myself signed in on a shared computer" case) rather than "that device can never obtain a new token again without the human logging in from scratch" (which is what you'd want for a genuinely stolen device/token). Closing that harder case requires Firebase's Admin-SDK-only `revokeRefreshTokens`, which would need a small Node-capable proxy (e.g., a single Google Cloud Function the Worker calls) — this is a deliberate, named V2 gap, not something glossed over, and it's left out of this pass because it means adding a second compute runtime/vendor for a threat model narrower than what most of this product's usage looks like.

**B. Firebase — two separate projects, one per environment** (mirrors the existing "no shared resources between dev and prod" rule already applied to every Cloudflare resource in `12`):
1. Create two Firebase projects at [console.firebase.google.com](https://console.firebase.google.com) — `agentdisk` (prod) and `agentdisk-dev`. (Recommended default, applied here rather than left as an open decision, precisely so this doesn't need to be asked mid-build: two projects, matching every other environment-separation decision already made in this design. Add these as GitHub Environment variables (not secrets, since they're not sensitive) on the `Development`/`Production` GitHub Environments `13` already created.
6. From the same config, note the **Project ID** specifically — this one additionally needs to reach the Worker as `FIREBASE_PROJECT_ID` (`07` PART 18.2), one value per environment, set via `wrangler secret put FIREBASE_PROJECT_ID --env <environment>` (not sensitive, but set the same way as the other config values for consistency).

**C. ### Baked-In Decisions — So You Don't Get Asked About These Mid-Build

These were genuinely open questions; they're resolved here, in advance, specifically so the build can run unattended:

- **Two Firebase projects, not one** (checklist B.1) — matches every other dev/prod separation decision already made.
- **Session revocation uses the local `users.session_revoked_after` timestamp** (PART 30.4), not a Firebase-Admin-SDK proxy. The Admin-SDK-only "true" revocation path is explicitly deferred to V2 and should not be built in this pass.
- **Plans/Stripe sync is push-on-edit plus a manual, diff-then-confirm pull** (`14` PART 29.6c) — never a silent overwrite in either direction.
- **Stripe integration stays at portal depth** (`14` PART 29.1) — no custom checkout or billing-management UI, regardless of how much easier the Plans screen makes admin-side pricing changes look.
- **The Admin Panel has no customer-impersonation feature** (`14` PART 28.3) — every staff action is *on* a workspace, never *as* the customer.
- Any remaining "Heads-up" item from `12`/`13` (one-Cloudflare-account-vs-two, preview-tier timing, etc.) is out of scope for this prompt — those belong to the infra prompt, already flagged there, and shouldn't be re-raised here.

### Build Order

**Phase 0 — Preflight verification, not assumption.** Programmatically confirm every item in the checklist above is actually present (both Firebase projects reachable, `FIREBASE_PROJECT_ID` set per environment, Stripe keys present, GitHub Environment variables populated) — fail loudly and list exactly what's missing rather than proceeding on a guess that it'll show up later. Inspect the existing repository in full, including whatever the original `11-backend-implementation-prompt.md` build already produced (custom password hashing, session/refresh-token routes, etc.) — this prompt replaces that subsystem, it doesn't build alongside it. **Stop-and-ask exception (the one place besides missing credentials this prompt should interrupt you):** if the `users` table already contains real rows with a `password_hash`, that's pre-existing real signups, not test data — stop and ask whether those are real users needing an explicit migration/import plan (Firebase supports importing pre-hashed passwords for a limited set of hash algorithms via `admin.auth().importUsers()`, which may or may not cover this project's original Argon2id hashes and needs a real decision either way) or safe to discard as pre-launch test data. Do not assume either way. **DoD:** every credential checked and confirmed present with a clear pass/fail report; the real-user-data check has been run and its result acted on (either confirmed test-data-only, or escalated per the exception above).

**Phase 1 — Firebase auth cutover, backend.** Implement the JWKS-cached JWT verifier (PART 30.2) as the new authentication step in the existing middleware chain (`06` PART 16.1's `withAuth`), replacing the old password/session verification entirely — the rest of that chain (scope resolution, workspace resolution, authorization, quota check) is unchanged. Apply the `05` PART 11.1 schema changes (`firebase_uid`, `session_revoked_after`, no `refresh_tokens` table) as a real migration. Remove the old `/login`, `/signup`, `/forgot-password`, `/reset-password` route handlers and any Argon2id/session-signing code entirely — this is deletion, not deprecation; leaving dead parallel auth code in place is worse than removing it. Implement the first-time-provisioning path (a verified token with an unseen `firebase_uid` creates the `users` row, and, unless joining an invited org, the initial `organizations`/`workspaces` rows) inside the authenticated request flow. Implement "log out everywhere" as the `session_revoked_after` write (PART 30.4), exposed both to the user themselves and to staff via `14` PART 27.5's `force-logout` endpoint. **DoD:** a real Firebase-issued ID token (from any of Email/Google/GitHub) authenticates a request end to end against live D1; a token from the *other* Firebase project (dev token against prod, or vice versa) is rejected on `aud` mismatch — prove this with a real test, not a code-review assumption; "log out everywhere" demonstrably forces a second, still-open session to re-authenticate on its next request.

**Phase 2 — Firebase auth cutover, `apps/web` frontend.** Integrate the Firebase JS SDK. Build Signup/Login/Forgot-Password/Reset-Password/Email-Verification (`03` §8.3–8.7, per the superseded notes already added there) as AgentDisk-branded screens backed by Firebase — Google, GitHub, email/password, and email-link all ship together (not staged across MVP tiers, since Firebase makes all four equally cheap). Attach the current ID token as a bearer header on every API call; let the Firebase SDK handle silent token refresh transparently. Wire "log out everywhere" (Active Sessions-equivalent UI, `03` §8.23 — note its data source changed, since there's no `refresh_tokens` table to list per-device sessions from any more; the simplest honest UI here is a single "Log out of all other sessions" action rather than a per-device list, since Firebase doesn't expose the kind of per-session inventory the original design assumed — flag this UI simplification explicitly rather than building a fake device list). **DoD:** a real signup via each of the three methods (Google, GitHub, email/password) completes and lands in a working, authenticated dashboard session against the live dev API, with zero console errors.

**Phase 3 — `apps/web`: the rest of the customer dashboard.** Build every remaining screen from `03` PART 8 (Overview, Files/Folders, Agents, API Keys, Workspace settings, Members, Webhooks, Usage, Activity, Billing, Danger Zone) exactly as `15-frontend-admin-billing-implementation-prompt.md` Phase 1 already specified — that phase's content is unchanged by the Firebase pivot and should be treated as still-authoritative here. Two specific pieces of that screen set were added after `15` was written and are easy to miss if you skim rather than read `03` in full: the Members screen's "Remove member" flow now includes a checked-by-default "also revoke every API key this person created" checkbox (`03` §8.22), and Workspace Settings' Danger Zone (`03` §8.21) deletion is a soft-delete-with-immediate-access-cutoff, not an instant physical purge — get both of these exactly as specified, not simplified. **Carry forward its Hard Gate, unweakened:** verify live that CORS is actually fixed (env-scoped origin, `OPTIONS` handled before auth — now doubly important, since every authenticated request is a real cross-origin bearer-token call from a real SPA) and that the API-key scope-naming conflict is resolved (bare `read`/`write`/`delete`/`list`, matching what the backend actually stores). **DoD:** identical to `15`'s Phase 1 DoD — a real user can complete the full core loop (create agent, mint scoped key, manage files, invite a member, register a webhook, view usage) against the live API with no screen backed by fixture data.

**Phase 5 — Stripe billing, both the customer-facing portal and the new admin-side plan sync.** Implement `14` PART 29.1–29.5 (customer creation, `POST /v1/billing/portal-session`, the `POST /v1/webhooks/stripe` handler, `billing_status` enforcement in the quota-check step) and PART 29.6 (the `plans` table, push-on-edit, diff-then-confirm pull) in full. **Phase 6 — Security, consistency, and test pass.** Run the full existing suite (`09-test-strategy-and-failure-modes.md`) plus everything `15`'s Phase 5 already specified (staff-login rate limiting, staff-session/customer-route cross-check, Stripe webhook signature rejection, `StaffScopedAccess` instantiation lint) plus these new cases this phase introduces:
- A token from the wrong Firebase project is rejected (Phase 1's DoD, re-verified here as part of the full suite); `session_revoked_after` actually blocks a stale token.
- The Plans push-to-Stripe endpoint fails loudly (and doesn't half-save) if the Stripe API call errors; the Plans pull-from-Stripe endpoint never applies a change without an explicit confirm step, verified by a test that tries to call it without one.
- **Workspace-status cascade** (`06` PART 16.1 step 5): with two workspaces and one active agent key in each, suspend one workspace — that workspace's key is rejected with a `WORKSPACE_SUSPENDED`-shaped error on its very next call, its `revoked_at` column is untouched, and the *other* workspace's key is completely unaffected. This is the artifact that turns "the API is complete" into "here's a link, go try it" — it should be short enough that you'd actually hand it to someone. **DoD:** both guides exist, and you (the agent) have personally walked through every step in each against the live deployed URLs and confirmed each one works exactly as written — not "should work based on the code."

### When to Stop and Ask

This prompt is deliberately structured so stopping should be rare. Use the format below only for the two named exceptions above (a missing pre-flight credential; discovering real pre-existing user data mid-migration) or a genuinely new fork the design documents don't cover:

```
Decision required:
Option A: <description>
Option B: <description>
Recommendation: <which, and why>
Reason: <the tradeoff driving the recommendation>
Impact: <what happens if we proceed with the recommendation vs. wait for an answer>
```

Do not use this format to re-open anything in the Baked-In Decisions section above — those are answered, not defaults awaiting confirmation.

### Quality Bar — What "Ready to Ask a Real User to Test" Actually Means Here

Not "the API is complete and the screens exist." Specifically: a stranger can go to `app.agentdisk.io`, sign up with a Google account (or GitHub, or email), land in a real working dashboard with zero setup help from you, create a workspace, upload a file, create an agent, mint a scoped API key, and successfully call the API or connect a real MCP client with that key — every step over the real domain, no console errors, no CORS failures. Separately, a staff member can sign in to `admin.agentdisk.io` with TOTP, find that stranger's new workspace, watch its real usage numbers, and — on the new Plans screen — change a price and see it actually land in Stripe and flow through to that customer's own Billing screen. And a test-mode Stripe subscription can complete a full lifecycle with `billing_status` and write-enforcement tracking it correctly at every step. All of it proven by you actually doing it against the live deployment and writing down what you saw (Phase 7), not inferred from the code being present.
