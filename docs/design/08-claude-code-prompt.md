## Prompt

You are implementing **AgentDisk**, a serverless, agent-native file storage platform, end-to-end, with minimal human intervention. The full product, UX, and technical design has already been completed and is provided in the accompanying design documents. Your job is to turn that design into a real, working, tested, deployed product — not to redesign it. Where the design documents leave a genuine implementation decision open, make a reasonable engineering decision, document it, and continue; do not stop to ask about things a competent senior engineer would just decide.

### Before Writing Any Code

1. **Inspect the repository.** If it already contains code, read it thoroughly before making any architectural decision or touching existing files. Do not destroy or rewrite existing functionality you don't yet understand. If the repo is empty, you're starting greenfield per the design documents.
2. **Read the design documents in this order** (they build on each other): `01-research-and-opportunity.md` → `02-product-and-mvp-scope.md` → `05-technical-architecture.md` → `06-security-privacy-legal.md` → `07-cloudflare-deployment-and-cost.md`. Skim `03-ux-architecture-and-screens.md` for context (the frontend implementation should follow `04-claude-design-prompt.md`'s output / Claude Design's produced designs if those exist in the repo, not re-derive UI from scratch).
3. **Do not start coding immediately.** Confirm you understand: the MVP-0/MVP-1/V2 boundary (`02`, section "PART 6"), the D1 schema (`05`, "PART 11"), the R2 key strategy (`05`, "PART 12"), the authorization middleware pattern (`06`, "PART 16.1" — this is the single most important pattern in the codebase; get it right before building anything on top of it), and the environment/deployment model (`07`, "PART 18").
4. **Produce a short implementation plan** (a markdown file, `docs/IMPLEMENTATION_PLAN.md`) restating the phase sequence below with your own task breakdown per phase, before writing the first line of application code. This is a planning artifact, not a design document — keep it short and update it as phases complete.

### Build Order — Follow This Sequence, Do Not Skip Ahead

**Phase 0 — Foundation.** Initialize the monorepo per `07-cloudflare-deployment-and-cost.md` PART 18.6's directory structure. Set up TypeScript strict mode, ESLint, Prettier, shared `tsconfig`/`eslint` config in `packages/config`. Set up the D1 database and initial empty migration. Set up `wrangler.toml` for local dev and preview environments (not production yet — no production resources until there's something worth deploying). Set up the CI pipeline skeleton (`06`'s and `07`'s content inform `PART 24`'s CI/CD design in the companion test-strategy document, `09`, and roadmap document, `10` — read those before building CI). **Definition of done:** `npm install && npm run build && npm test` all succeed on an empty-but-scaffolded repo; a "hello world" Worker deploys to preview and responds on `/v1/healthz`.

**Phase 1 — Data layer.** Implement the full D1 schema (`05` PART 11.1) as migrations. Implement the `WorkspaceScopedFiles`-style repository pattern (`06` PART 16.1) for every table — this is the tenant-isolation enforcement mechanism; it must exist before any route handler is written, not retrofitted after. Write unit tests proving a repository instance scoped to workspace A can never read or write workspace B's rows, even if asked to (this is a security-critical test, not an afterthought — see `09-test-strategy-and-failure-modes.md`). **Definition of done:** migrations apply cleanly to a fresh D1 instance; repository-layer unit tests pass, including the cross-tenant-isolation tests.

**Phase 2 — Authentication.** Implement human auth (email/password with Argon2id hashing, magic link, session + refresh-token cookies with rotation — `06` PART 15.1/15.2/16.5/16.6) and API-key auth (generation, hashing, verification, scoping — `06` PART 15.3/16.4). Implement the full authorization middleware chain (`06` PART 15.2/16.1) as the one place every request passes through. Do not implement GitHub OAuth yet (that's Phase 6 territory per the MVP-0/MVP-1 boundary) — build the interface so it can be added without restructuring auth, but don't build it now. **Definition of done:** signup → verify email → login → authenticated request → logout all work end-to-end with real tests, not mocks, against a local D1 instance; a forged/expired/revoked token is correctly rejected with the exact error codes from `05` PART 13.

**Phase 3 — Storage core (R2 + files/folders).** Implement the R2 object-key strategy (`05` PART 12.1), the presigned-upload/download flow (`05` PART 12.2/12.3), folder CRUD, file CRUD (create/get/list/update/move/copy/delete/restore), quota enforcement at write time (`06` reference to workspace counters), and soft-delete + the hourly reconciliation Cron job (`05` PART 10.7/10.8). Implement path validation/normalization (`06` PART 16.12) as a shared, tested utility used by every path-accepting endpoint — write explicit tests with real path-traversal payloads (`../../etc/passwd`-style strings) proving they're rejected, not just trusted to "probably work." **Definition of done:** a real file can be uploaded via a presigned URL, listed, downloaded, moved, and deleted-then-restored-within-grace-period, all via integration tests hitting real (preview-environment) R2 and D1 — not mocked.

**Phase 4 — REST API.** Implement every endpoint in `05` PART 13's table, generating the OpenAPI spec from the route definitions (or hand-writing the OpenAPI spec as the source of truth and generating route types from it — pick one direction and be consistent; do not let the two drift, which is the exact documented failure AgentStorage's own docs suffered from, `01` PART 2.10). Implement the uniform error envelope and the full error-code catalogue (`06` PART 17.4) consistently across every handler. Implement rate limiting per `05` PART 10.9 (WAF rules for the coarse cases, KV counters for the rest). **Definition of done:** every endpoint has at least one happy-path integration test and one authorization-denial test; the generated OpenAPI spec validates against the actual deployed API via a contract test in CI.

**Phase 5 — MCP server.** Implement the MCP server (`05` PART 14) as a thin layer over the *same* service functions Phase 4's REST handlers call — if you find yourself duplicating business logic between a REST handler and an MCP tool handler, stop and refactor to share it; this is not optional, it's the core architectural decision in `05` PART 14.1. Implement all 10 tools from `05` PART 14.4 (search_content can be a V2 stub that returns the documented `indexingNotEnabled` response rather than a 501 — build the honest "not yet" response, not a fake success). Implement per-session MCP rate limiting via the Durable Object pattern described in `05` PART 10.9/14.3. **Definition of done:** a real MCP client (test against Claude Code or the MCP inspector tool) can connect, discover tools filtered to its key's scope, and successfully call each tool against a real workspace; a scope-violating tool call is rejected with the correct MCP-shaped error, not a silent no-op.

**Phase 6 — Dashboard frontend.** Implement every screen from `03-ux-architecture-and-screens.md` PART 8 (or from Claude Design's output if that exists in the repo — treat it as the visual source of truth, this document as the interaction/copy source of truth) for the MVP-0 screen set first, then MVP-1 screens. Wire every screen to the real API — no mock data left in the shipped build. Implement GitHub OAuth here (this is the right phase for it, per `06` PART 15.1's sequencing decision). **Definition of done:** a real user can complete every MVP-0 flow (signup → create workspace → create agent → create key → upload/browse/delete files → view usage) through the actual UI against the actual API, verified by Playwright E2E tests, not just manual click-through.

**Phase 7 — Security hardening pass.** Before calling MVP-0 done, explicitly walk `06-security-privacy-legal.md` PART 16 top to bottom and verify each control is actually implemented, not just designed: CSRF, CORS, XSS escaping, parameterized-query enforcement (add a lint rule if one doesn't already exist), SSRF protection on webhook URLs (even if webhooks are MVP-1, build the URL-validation utility now so it's not rushed later), secret-redaction in logs, and the full security test-case list in `09-test-strategy-and-failure-modes.md`. **Definition of done:** every test case in that document's security section passes; run the codebase through whatever static-analysis/dependency-scanning tooling is available (e.g., `npm audit`, a SAST tool if configured in CI) and triage findings — do not silently ignore a finding, either fix it or document why it's a false positive/accepted risk.

**Phase 8 — Testing completion.** Fill in any remaining gaps against `09-test-strategy-and-failure-modes.md`'s full test matrix (unit/integration/E2E/security/performance). Do not consider any phase "done" if its tests are failing, skipped, or mocked in a way that hides a real integration gap.

**Phase 9 — Deployment to production.** Follow `07-cloudflare-deployment-and-cost.md` PART 18.3's exact deployment sequence. Create production Cloudflare resources, configure production secrets, run migrations against production D1, deploy the Worker and Pages projects, configure the domain per PART 18.4, and run the smoke test suite against the live production URL before considering the deploy complete.

**Phase 10 — Production hardening.** Wire up observability per `07` PART 18.5 (Analytics Engine dashboards, error alerting). ### Coding Principles — Non-Negotiable

- **TypeScript strict mode everywhere.** No `any` without an explicit, reviewed justification comment. No `@ts-ignore` without the same.
- **Modular architecture, small functions.** A route handler is thin — authenticate/authorize/validate, call a service function, format the response. Business logic lives in `services/`, never inline in a route handler.
- **Clear interfaces.** Every service function has an explicit input/output type, not an inferred `any`-shaped object passed around.
- **Minimize dependencies.** Before adding an npm package, check whether the Workers runtime's built-ins (Web Crypto, `fetch`, `URL`, etc.) already cover the need. Do not add a framework or ORM that assumes a long-running Node process — everything must run correctly in the Workers runtime's constraints.
- **No unnecessary infrastructure.** Do not introduce Redis, a managed Postgres, a container platform, or any always-on server. If you believe one of these is genuinely required, stop and present the decision explicitly (format below) rather than adding it silently.
- **Secure defaults.** Every new endpoint defaults to requiring authentication and the narrowest plausible authorization; an endpoint is public only if there's an explicit, documented reason (matches `05` PART 13's table — do not add an endpoint not in that table without flagging the addition).
- **Environment variables for config, secrets via `wrangler secret`, never hardcoded, never committed.** Add any new secret to `.dev.vars.example` (placeholder only) and to `07-cloudflare-deployment-and-cost.md`'s secrets list (update the doc — don't let it drift).
- **Input validation at every boundary.** Every route handler validates its input against a schema before touching business logic (reuse one validation library consistently across the codebase — pick one in Phase 0 and stick with it).
- **Structured errors, structured logging.** Use the error catalogue (`06` PART 17.4) and the logging redaction rules (`06` PART 16.18) as hard requirements, not suggestions.
- **Deterministic tests.** No test that depends on real wall-clock timing races, unseeded randomness, or external network calls that aren't explicitly mocked/pointed at a preview environment. Flaky tests get fixed, not retried-until-green or deleted.
- **Avoid premature abstraction.** Build the concrete thing the design document specifies first; generalize only when a second real use case actually appears, not speculatively.

### Testing, Linting, Type-Checking, Build Discipline

After every major feature (roughly: after each numbered phase above, and after any significant sub-feature within a phase): run the full test suite, run the linter, run the type checker, run the build. **Fix failures before moving on — never move to the next phase with a red test suite, a lint error, a type error, or a broken build.** Never silently ignore an error, disable a failing test, or comment out a broken assertion to make CI green — if a test is wrong, fix the test with a clear explanation of why it was wrong; if the code is wrong, fix the code. Never use a fake/mock implementation where the design document calls for a real one (e.g., do not mock R2 in an "integration test" that's supposed to prove real upload/download works — use a real preview-environment R2 bucket for that tier of test, and reserve mocks for true unit tests of business logic in isolation). Never leave a `TODO` placeholder for core functionality described in the design documents — either implement it or explicitly flag it as a deferred decision using the format below.

### When You Must Stop and Ask

Continue autonomously through everything covered by the design documents. Stop and ask **only** when a decision is not covered by the design documents and carries real, hard-to-reverse consequences — for example, the actual legal entity name for the Terms of Service/Privacy Policy placeholders (`06` PART 17.2/17.3), the actual third-party email provider or AI processor to name in the Privacy Policy (`06` PART 17.2 Sections 11–12), or a genuine architectural fork the design documents left open. When you do stop, use exactly this format:

```
Decision required:
Option A: <description>
Option B: <description>
Recommendation: <which, and why>
Reason: <the tradeoff driving the recommendation>
Impact: <what happens if we proceed with the recommendation vs. wait for an answer>
```

Do not use this format, and do not stop, for questions a competent senior engineer would just answer from the design documents or reasonable convention (variable naming, which testing library, exact retry-count tuning, etc.) — make the call, note the assumption briefly in a code comment or the implementation plan doc, and keep going.

### Documentation Obligations

Keep `docs/ARCHITECTURE.md`, `docs/SECURITY.md`, `docs/API.md`, `docs/MCP.md`, `docs/DEPLOYMENT.md`, `docs/DATABASE.md`, `docs/STORAGE.md`, `docs/TESTING.md`, and `docs/COST.md` (per `10-cicd-docs-roadmap-and-recommendation.md` PART 25) up to date **as you build**, not as a final documentation pass — a schema change updates `DATABASE.md` in the same PR, a new endpoint updates `API.md`/the OpenAPI spec in the same PR. Documentation that drifts from the code is worse than no documentation (this is, again, the exact AgentStorage failure mode from `01` PART 2.10 — do not repeat it).

### Quality Bar

The finished product should feel like a real SaaS product, not a prototype: polished, consistent UI following `04-claude-design-prompt.md`'s design system exactly; secure authentication and authorization with no shortcuts taken versus `06`'s security model; genuinely isolated tenants (prove it with tests, not just code review); reliable storage with the soft-delete/reconciliation safety net actually working; clean, documented APIs; working MCP support; error messages that match the catalogue; a responsive, accessible UI; automated tests covering the matrix in `09-test-strategy-and-failure-modes.md`; up-to-date documentation; a real production deployment on the real domain; basic observability; and costs tracking the model in `07-cloudflare-deployment-and-cost.md` PART 19. "It compiles and the happy path works in a demo" is not the bar — "a stranger could rely on this" is the bar.
